# s2s-service-mesh

Small demo: three Go apps talk to each other **through Istio**, while the apps themselves run in **Docker** and Istio’s control plane runs in a **local Kubernetes** cluster (Kind).

This doc explains **who does what** and **how networking works**, in plain language.

---

## The big picture (two machines in one laptop)

Think of two layers:

| Layer | Where it runs | Job |
|--------|----------------|-----|
| **Control plane** | Kind cluster (Kubernetes) | **istiod** — the “traffic boss.” It hands out config, certificates, and service names to sidecars. |
| **Data plane** | Docker Compose | Three **apps** + three **Istio sidecars** (Envoy proxies). They do the real HTTP and encrypted mesh traffic. |

The apps are **not** inside Kubernetes pods. They are **external workloads**: Docker containers that still join the mesh because each one has an Istio sidecar.

```
  Your browser / curl
         |
         v
  localhost:3000 / :4000 / :5001  (Docker published ports)
         |
         v
  +---------------- Docker network "mesh" ----------------+
  |  order-service  +  order-istio (sidecar)              |
  |  payment-service + payment-istio                      |
  |  notification-service + notification-istio            |
  +---------------------------|---------------------------+
                              |
                              |  TLS + config (port 31215)
                              v
                    Kind cluster: istiod
                    + K8s objects in mesh-workloads
                      (Services, WorkloadEntries, ...)
```

## The three apps (what they do)

| App | Port inside container | On your Mac (host) | Role |
|-----|------------------------|--------------------|------|
| **order** | 3000 | `http://localhost:3000` | Entry point. For `/orders/{id}` it calls payment, then notification, and returns one JSON blob. |
| **payment** | 4000 | `http://localhost:4000` | Returns fake payment JSON for `/payments/{id}`. |
| **notification** | 5000 | `http://localhost:5001` | Host maps **5001→5000** (5000 is often busy on Mac). POST `/notifications/{id}`. |

**Important:** Order’s Go code uses simple hostnames:

- `http://payment-service:4000/...`
- `http://notification-service:5000/...`

Those names work because all services share the same Docker network **`mesh`**. Istio’s sidecar sits in front of each app and can add mTLS, policies, and telemetry without changing that Go code.

---

## Sidecar pattern (why two containers per service)

Each app container has a buddy: **`istio/proxyv2`** with `network_mode: service:<app>`.

That means:

- The **sidecar shares the app’s network stack** (same IP, same ports from the outside).
- Traffic to port 3000/4000/5000 hits **Envoy first**, then Envoy forwards to the Go process on localhost inside the pair.
- Outbound calls from the app also go through Envoy (transparent redirect with `NET_ADMIN`).

So “service mesh” here = **every hop goes through Envoy**, guided by **istiod**.

Files that boot each sidecar live under `istio/workloads/<name>-config/` (generated by `bootstrap-workloads.sh`):

- `mesh.yaml` — how to find istiod
- `istio-token` — proves identity to the cluster (lab secret; regenerate locally)
- `root-cert.pem` — mesh trust anchor

## What runs in Kubernetes (and why)

Nothing runs your Go binaries in K8s. Kubernetes only holds **Istio bookkeeping**:

| Object | Purpose |
|--------|---------|
| **Namespace `mesh-workloads`** | Home for mesh-related resources. |
| **ServiceAccounts** `order`, `payment`, `notification` | Identity for each workload in the mesh. |
| **Services** `order`, `payment`, `notification` | Logical names and ports Istio uses for routing (3000, 4000, 5000). |
| **WorkloadGroup** (per app) | Template for “how an external VM/container should look” to Istio. |
| **WorkloadEntry** (created by sync script) | **Actual Docker IP + port** so istiod knows where each container lives. |

When you `docker compose up`, container IPs can change. Run **`./istio/scripts/sync-workload-entries.sh`** so Kubernetes gets the current IPs. Without that, the mesh may route to stale addresses.

## How istiod talks to Docker sidecars

Kind runs inside Docker. Your sidecars run in Docker too, but on the **host** network namespace for each app.

1. **Kind** maps cluster port **31215** → istiod’s discovery port (**15012**) — see `kind-config.yaml` and `istio/istio-nodeport.yaml`.
2. Each app container has **`extra_hosts`**: `istiod.istio-system.svc` → **`host-gateway`** (your Mac/Docker host), so the sidecar can reach that NodePort.
3. Sidecar config points at **`istiod.istio-system.svc:31215`** (patched in `patch-mesh.sh`).

So: **sidecars pull config from Kind over the host**, not from inside the Kind node network.

## One request walkthrough

You run:

```bash
curl http://localhost:3000/orders/demo-1
```

Rough steps:

1. **Host → Docker** — TCP to order’s published port 3000.
2. **order-istio (inbound)** — Envoy accepts, may apply mesh rules, forwards to Go on loopback inside the shared network namespace.
3. **order-service (outbound)** — Go calls `payment-service:4000`. DNS resolves on the `mesh` network. Traffic is captured by **order-istio (outbound)**.
4. **Mesh routing** — Envoy uses istiod’s view: Service `payment` → WorkloadEntry IP for payment container → often **mTLS** to **payment-istio**.
5. **payment-istio → payment-service** — Inbound proxy → Go returns JSON.
6. Same pattern for **notification-service:5000** (POST).
7. Order merges JSON and responds to you.

From the outside it looks like normal HTTP on localhost. Between sidecars, Istio can use encrypted identity-aware traffic.

## Scripts (what to run when)

| Script | When |
|--------|------|
| `./istio/scripts/install-istio-kind.sh` | Once (or after recreating Kind): install istiod with NodePort **31215**. |
| `./istio/scripts/bootstrap-workloads.sh` | After cluster is up: apply K8s YAML + generate `*-config/` for sidecars. |
| `docker compose up --build -d` | Start apps + sidecars. |
| `./istio/scripts/sync-workload-entries.sh` | **After every compose recreate** — refresh Docker IPs in WorkloadEntries. |
| `./istio/scripts/preload-istio-images.sh` | Pull Istio images on the **host** + `kind load` pilot (use on corp laptops). |
| `./istio/scripts/setup-corporate.sh` | **Recommended on company laptops:** Kind (if needed) → preload → Istio → bootstrap → compose → sync → test. |
| `./istio/scripts/up.sh` | Preload + install + bootstrap + compose + sync + test curl. |

## Company laptop (ImagePullBackOff / blocked Docker Hub)

No setup can work if **nothing** is allowed to download container images. This repo assumes you can **`docker pull`** on the laptop (often with **VPN** or an **HTTP proxy**). Kubernetes inside Kind is configured **not** to pull from the internet if the image is already on the node.

**One command** (Ubuntu, from repo root):

```bash
chmod +x istio/scripts/*.sh
./istio/scripts/setup-corporate.sh
```

What it does:

1. Creates Kind with `kind-config.yaml` if missing (host port **31215**).
2. **`preload-istio-images.sh`** — `docker pull` `pilot` + `proxyv2`, then **`kind load`** pilot into the cluster.
3. Installs **minimal** Istio (istiod only, fewer images) with **`imagePullPolicy: IfNotPresent`**.
4. Regenerates sidecar configs, starts Compose, syncs WorkloadEntries, runs a smoke `curl`.

**Internal mirror** (copy `.env.example` → `.env` or export):

```bash
export ISTIO_HUB=registry.yourcompany.com/istio
export ISTIO_TAG=1.31.0
export ISTIO_PROXY_IMAGE=registry.yourcompany.com/istio/proxyv2:1.31.0
./istio/scripts/setup-corporate.sh
```

**If istiod still fails:**

```bash
./istio/scripts/preload-istio-images.sh
istioctl install -y -f istio/istio-nodeport.yaml \
  --set values.global.imagePullPolicy=IfNotPresent
./istio/scripts/wait-istiod.sh
```

## Repo layout (short)

| Path | Meaning |
|------|---------|
| `order-service/`, `payment-service/`, `notification-service/` | Go HTTP servers |
| `docker-compose.yaml` | Apps + Istio sidecars on network `mesh` |
| `kind-config.yaml` | Kind cluster with host port **31215** |
| `istio/k8s/` | Namespace, service accounts, K8s Services |
| `istio/workloads/*-workloadgroup.yaml` | External workload templates |
| `istio/workloads/*-config/` | Sidecar bootstrap (generated; includes tokens) |
| `istio/scripts/` | Install, bootstrap, sync, `up.sh` |
| `*/envoy.yaml`, root `envoy.yaml` | **Old static Envoy demo** — not used by the Istio Compose setup |
